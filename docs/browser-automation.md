# 브라우저 자동화 노하우

## URL과 초기화된 앱 탭은 다르다

상태 기반 웹앱은 주소가 같아도 `GET`으로 새 탭을 열었을 때 같은 화면이 보장되지 않는다.
런처가 `window.open`, `window.name`, opener, 프레임 초기화, 일회성 세션 상태 등을 만든 뒤에야
정상 동작하는 앱이 있기 때문이다.

비즈플레이 카드영수증이 실제 사례다. 정상 탭의 주소는
`https://webank.appplay.co.kr/rcard_main.act`지만 이 URL을 새 탭에서 다시 열면 미결의 목록이
나오지 않을 수 있다. 따라서 다음 순서를 지킨다.

1. 열려 있는 탭들의 모든 프레임을 **URL이 아니라 화면 내용**으로 검사한다.
2. `대기(n)`, `결의상태`, 날짜가 있는 영수증 표가 보이는 기존 `tabId`를 우선 사용한다.
3. 기존 탭을 재사용했다면 자동화가 끝나도 사용자 탭을 닫지 않는다.
4. 기존 정상 탭이 없을 때만 기억한 URL이나 런처 탐색으로 폴백한다.
5. 내부 프레임은 최상위 로드 뒤 늦게 생길 수 있으므로 이름 하나(`eusr_9001`)에 의존하지 않고
   모든 프레임을 일정 시간 반복 검사한다.

회귀 검사는 새 `rcard_main` 요청이 발생하지 않는지와 사용자 탭이 유지되는지를 함께 확인한다.
주소 인식만 검사하면 정상 탭을 찾고도 URL만 저장한 뒤 새 탭을 여는 퇴행을 잡지 못한다.

## 합성 클릭과 팝업

페이지가 신뢰 사용자 제스처(`isTrusted`)를 요구하면 `element.click()`이나 합성 포인터 이벤트로
`window.open`을 호출해도 팝업이 차단된다. 확장에서는 MAIN world에서 `window.open`을 잠시
가로채 대상 URL을 얻고, `chrome.tabs.create`로 직접 연다. 가로챈 함수는 즉시 원복한다.

팝업 탭은 이미 로드가 끝난 뒤 리스너가 붙을 수 있다. `tabs.onUpdated`만 기다리지 말고 현재
`tab.status`도 즉시 확인하며, 반드시 타임아웃을 둔다.

## 외부 시스템 쓰기 안전 규칙

조회와 제출은 메시지 타입과 UI 흐름을 분리한다. 결과 화면을 보는 것만으로는 쓰기가 발생하면
안 된다.

1. 조회 결과에서 정확한 대상 건수·금액·제안값을 보여준다.
2. `대상 확인` 뒤 실제 외부 쓰기임을 알리는 두 번째 확인 버튼을 보여준다.
3. 두 번째 확인 뒤에만 `correction-submit` 또는 `expense-submit` 메시지를 보낸다.
4. 제출 직전에 미결의 행을 key(일시·사용처·금액)로 다시 찾아 전부 일치할 때만 진행한다.
5. 결재 용도와 결재선은 최근 사용값에 의존하지 않고 명시적으로 선택한다.
6. e2e는 확인 전 서버 쓰기 0건과 확인 후 정확한 요청 수를 모두 검증한다.

실계정에서는 자동 e2e로 상신하지 않는다. 가짜 서버에서 전체 흐름을 검증하고, 실계정 검증은
사용자가 화면의 대상과 금액을 직접 확인한 뒤 한 건으로 진행한다.
